# LLM Web Observer 身份归属能力与精确集成指南

> 面向客户：说明产品三种身份归属模式的能力边界、精度承诺，以及需要精确归属时的可选集成方式。
> 关键结论：**零侵入部署即可获得全量 LLM 调用审计；精确到"人"的归属是可选增强，不需要修改业务系统也能运行。**

## 一、三种归属模式总览

| 模式 | 业务侧改动 | 归属精度 | 典型场景 |
|---|---|---|---|
| **T1 时间窗推测**（默认开启） | 无 | 低：5 分钟窗口内全局最新客户端信标，多用户并发时会错配 | 单人使用、演示、PoC |
| **T1 入站关联**（默认开启） | 无 | 中-高：按入站请求时间窗 + 凭证哈希归属，会话首轮归属后整线程继承（sticky） | 中低并发生产环境（≤ 数十同时在线用户） |
| **T2 精确头注入**（可选） | 业务系统在 LLM 出站请求追加内部头 | 100%：每个 LLM 调用精确到 user / session / task | 高并发、合规审计、需要真实用户名的场景 |

三种模式**自动叠加降级**：优先 T2 精确头 → 无头则 T1 入站关联 → 都没有则时间窗推测。每一条事件都带 `client.identity.confidence` 字段如实标注归属依据：

`exact`（精确头）> `sticky` / `inferred`（入站关联）> `inferred-ambiguous`（入站窗口内出现多个用户，已标注存疑）> `temporal`（纯时间窗推测）

## 二、零侵入模式（T1）的工作原理与边界

### 原理

```
用户请求 ──► 业务网关(Nginx)
              │ mirror（镜像元数据：方法/路径/Authorization 哈希，不含请求体）
              ▼
         Observer collector ──► 凭证哈希 = 稳定伪身份（u-xxxxxxxx，原始 token 永不落库）
                                        │
业务系统 ──LLM 出站──► 网关(mitmproxy) ──┤ 时间窗重叠匹配 + 会话粘性
                                        ▼
                              事件归属到伪身份用户
```

- 入站 API 请求（含 WebSocket 升级请求）被网关镜像给 Observer；凭证（Authorization / 会话 Cookie）以加盐哈希转成**稳定伪身份**
- LLM 出站调用发生时，Observer 在入站请求时间窗内寻找凭证：REST 请求回溯 30 秒，WebSocket 会话回溯 30 分钟
- 首轮归属成功后，`conversation_id → 用户` 的映射固化，后续整条会话继承（sticky），不受时间窗过期影响
- 窗口内出现多个不同凭证时，不固化归属，事件标记 `inferred-ambiguous` 存疑

### 边界（如实告知）

1. **伪身份 ≠ 真实用户名**：同一用户换凭证（重新登录）会得到新伪身份；需要"人话的名字"请用 T2
2. **高并发歧义**：多个用户在秒级同时请求且业务走长连接时，首轮归属可能存疑（会标记）
3. **会话碰撞**：两个用户发送完全相同的首条消息时，可能被归入同一 conversation 线程（T2 的显式 session 可彻底解决）

## 三、精确模式（T2）集成方式

### 方式 A：X-LWO-* 内部头（推荐，改动最小）

业务系统在发起 LLM 出站请求时附加内部头，网关会在转发上游前**剥除**（不会泄漏给模型供应商）：

| Header | 必填 | 内容 |
|---|---|---|
| `X-LWO-User` | ✅ | 用户 ID（服务端会话中取得，禁止信任客户端传入值） |
| `X-LWO-Username` | 建议 | 显示名，控制台直接展示 |
| `X-LWO-Session` | 建议 | 会话 ID，实现按用户/线程分组 |
| `X-LWO-Platform` | 建议 | android / web / ios / cli |
| `X-LWO-Task` | 可选 | 后台任务标注（title / recommendations 等） |

实现注意事项、调用点封装建议与验收标准见《deeptutor-identity-headers.md》（首个落地集成案例文档）。

> ⚠️ 若业务系统的 HTTP client 是复用实例（如 OpenAI SDK 的 AsyncOpenAI），身份头**必须按请求**通过 `extra_headers` 注入，不能放进 client 级 `default_headers`——否则并发请求会串身份。

### 方式 B：OTLP / OpenTelemetry（规划中）

客户已有 OTel 基建时，可通过标准 OTLP 协议推送带用户属性的 span，Observer 作为后端之一接入。适合不想为审计引入私有头协议的企业客户。当前版本暂未开放，路线图项目。

### T2 验收标准（交付时逐项验证）

1. 两个用户 1 分钟内交替发消息，归属 100% 正确（`confidence: exact`）
2. 后台任务（标题生成、推荐等）也携带用户身份，不出现"无主"事件
3. 出站上游（模型供应商）收到的请求中不含任何 `X-LWO-*` 头
4. 用户切换会话后，新会话归属正确且不继承旧会话身份

## 四、选购/升级建议

- **内测、单人使用**：T1 即可，不要为归属精度投入业务改造
- **开放注册、生产运行**：T1 入站关联已可满足运营级审计；发现 `inferred-ambiguous` 比例升高时再上 T2
- **合规场景**（金融、医疗、教育监管）：直接 T2，`exact` 置信度是审计报告的硬要求
